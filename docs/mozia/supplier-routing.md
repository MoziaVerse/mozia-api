# 供应商资源池与动态路由

实现分支：`codex/adaptive-supplier-routing`，基于 `codex/supplier-routing` 的 `0a19a01ae`。复用 new-api 的渠道、鉴权、计费、Redis、模型更新检测和后台任务，没有新增运行依赖。

## 当前策略

新建规则默认 **可用性优先，性能分流，兼顾成本**（`adaptive`）。客户售价独立，供应商份额随真实调用表现变化。

1. 保留权限、模型版本和能力满足要求的渠道，并检查选填的容量限制。首期支持 OpenAI 兼容文本 Chat Completions，包括流式、工具调用及 JSON 输出。
2. **可用性独立判断**：正常池优先，没有正常池时才用可用性降级池；故障或过载冷却期间不派发。速度不足不会导致可用性降级或冷却。
3. **性能决定流量比例**：同一可用性层内，默认每项速度指标至少 90% 的有效请求达标，才属于性能达标池。达标池获得默认 90% 的非试运行流量，偏慢或性能样本不足的池共享剩余 10%；仅有一组时获得全部常规流量。性能不足不会永久排除任何池。
4. **性能达标组内优化采购成本**：同池选择最低成本渠道作为代表，同价轮换，复制渠道不增加池权重。第三方按 `max(1, round(1000 × (最低费用 / 本池费用)²))` 平滑加权，成本 1:2 对应约 80%:20%。渠道 Priority 不覆盖新模式。
5. **性能未达标组内优先改善体验**：按速度接近目标的程度和请求达标比例加权，所有池保留正权重；该组不按采购成本排除候选。因此全部偏慢时，也不会单纯选择最便宜的池。
6. 新池、样本过期或故障冷却后的池进入试运行。有成熟候选时共享默认 5% 请求预算，每池最多一个试运行在途请求；全部为新池时用此并发限制启动。存在试运行池时，90%/10% 性能配比作用于剩余常规流量，不能与 5% 直接相加。

**自部署渠道：** 沿用 `channels.deployment_type`（`unknown/self_hosted/third_party`）。自部署无需采购报价，在同一可用性层的性能达标组内优先于第三方，包括明确零报价的第三方。多个达标自部署池均衡分配，同池渠道轮换。偏慢的自部署池也只参与性能分配；达标自部署不会挤掉其他偏慢池的保留流量。容量、故障冷却和试运行限制仍然执行。未分类渠道仍需完整报价，旧模式保持原意。

自部署暂不核算基础设施成本：历史调用使用 `cost_status=not_applicable`、金额 0、无币种，不能解释为已结算的真实成本。已有采购报价保留但不参与自部署路由，改回第三方后可恢复使用。部署类型修改与改价共用 SQL 事务及 Redis 发布屏障；在途调用使用原快照。修改后无有效候选报价或发布前置条件不满足时整体回滚；返回 `procurement.application=pending` 时表示已保存、待生效。

**采购估算：** 输入复用 Token 估算，输出使用同模型、分组、流式/非流式近期成功调用的平均输出数，无样本时参考 512，并受请求显式输出上限约束。所有池使用相同估计量，不把容量安全余量或缓存折扣用于压低报价。实际费用使用具体执行渠道的报价快照和原始 usage。

**报价要求：** 非自部署渠道在同一规则使用 CNY 或 USD 中的一种；支持文本 `input`、`output`、可选 `cache_read` 的每百万 Token 单价，或 `per_request` 的 `base_price`。缺字段、无报价或复杂计价模式不能参与成本路由。按次成功调用无需 Token usage 也可核算；自部署不要求报价，也不参与币种一致性判断。

报价修改与资源修改共用发布屏障，SQL 事务保存后发布 Redis 运行版本。返回 `application=pending` 时表示已保存、待生效；发布完成前保守拒绝派发。新请求不能使用过时版本的报价预占容量，已准入的调用继续使用其报价快照。

## 健康与容量

| 参数 | 初始值与含义 |
| --- | --- |
| 统计窗口 | 优先最近五个分钟桶；可用性样本不足时向前累计至足够，最多 60 个分钟桶。实时排行榜仍只显示五分钟 |
| 有效样本 | 可用性至少 20 次有效调用；性能另需 20 个速度样本，流式还需 TTFT 样本。缺少速度数据不阻止可用性成熟 |
| 最低成功率 | 95%；低于门槛进入降级层 |
| 性能目标 | 默认每项指标至少 90% 请求达标：流式 TTFT ≤ 5000ms、有效吞吐 ≥ 10 tokens/s。各平台模型由管理员校准 |
| 偏慢池流量 | 默认共享 10% 非试运行流量，允许配置 1–49%；0 或缺省使用默认值。只有偏慢池时不限制总份额 |
| 故障冷却 | 失败率 ≥ 20% 或连续三次明确故障，默认冷却 30 秒 |
| 过载 | 429 独立退避：无 Retry-After 时 1、2、4…秒，上限为故障冷却秒数；有 Retry-After 时按其值，最多一天。恢复成功后重置退避，不清除可靠性样本 |
| 恢复 | 故障冷却后重新试运行；可用性降级须在两个不同分钟有新的达标观测才恢复，期间再次不达标则重新计数 |

健康数据按资源池、模型版本、分组、流式/非流式和规则隔离。首 Token 或吞吐目标变更时，旧目标下的达标计数不再复用；仅修改价格不会重置样本。性能组采用最差单项达标比例，要求每项分别达标；不等于统计所有指标同时达标的联合比例。有效吞吐为实际输出 Token 数 / 上游调用总耗时，包含等待；只用完整成功且有原始 usage 的调用计算。毫秒分辨率下的正耗时最低按 1ms 记录。人工探测和观察建议不训练真实流量指标。

401/402/404/408、5xx、网络或上游超时、断流计入故障；用户输入错误和平台总预算耗尽不归责供应商。已经完成的成功响应，不因客户端随后断开而改为取消。正常完成在响应结束前结算并释放准入，避免后续请求误撞试运行并发上限。

**容量独立选填：** 池的并发、RPM、TPM 留空（API 中为 0）表示未声明。模型级 0 继承池；两处都为 0 时该维度不设配置上限。已填写的限制由所有渠道、Key 和网关共享，并通过 Redis 原子执行。

RPM 是最近 60 秒开始的请求数；TPM 按开始时刻预占“保守输入估算＋输出上界”，完成后用原始 usage 校正。不是供应商按生成时刻计算的 Token 流量协议。客户端未给输出上限时仍发送已验收的模型上限。

未发送可撤销预占；明确结束释放并发，真实调用不退 RPM。执行结果未知时保留并发至“请求总时限＋上游保证执行/排队期限”，费用待核对。容量未声明不代表无限容量，需依靠实测过载和冷却反馈。

## 管理入口

- `/suppliers`：供应商列表、档案、调度策略。新规则配置适用模型、分组/客户、候选供应商，并分别配置可用性要求、性能目标及高级试运行参数，无需填写份额。
- `/resource-pools`：资源池列表、筛选、抽屉。基础信息 → 可选共享容量 → 模型规格和可搜索的多选渠道 → 一次保存。模型与绑定在同一事务内提交。
- `/system-settings/billing/channel-costs`：现有渠道采购价。规则表单提供入口；报价影响动态路由及采购核算，客户计费独立。
- `/supplier-monitor`：分为实时质量排行和历史监控。实时每 10 秒刷新；历史按时间范围、供应商和完整模型名称查询，调用明细分页展示，并保留采购费用及对账。

记录仍独立保存：更新携带当前 ETag，创建使用幂等键；可视化和高级 JSON 共用草稿。切换只检查结构，提交才检查业务值。通用 Option 和整包 JSON 写入不能绕过记录 API。

采购详情与费用汇总要求 `model_pricing:read`，改价与核对要求对应写权限。普通配置与版本详情不暴露采购快照。路由配置发布要求 `supplier_routing:publish`，配置与普通运行指标沿用 `channel:read`。

实时接口 `GET /api/channel/supplier-routing/realtime` 只读 Redis，窗口为当前分钟及前四个分钟桶，按调用完成时间统计。页面分别展示当前可用性状态和最近选路时的性能状态，并展示速度达标率、选路原因及当时样本窗口/样本量/可用率；这些选路详情是快照，不是即时流量比例承诺。相同模型、版本、分组、流式类型和规则内，以资源池为单位，按成功率降序、429 比率升序、平均吞吐降序、平均 TTFT 升序排名；低于规则最小样本数不编号。排行仅用于观测，不引入新的路由评分或改变权重。失败/429 在冷却代次切换后仍保留到窗口过期，探测、建议、未发送、调用方错误不计入质量；实时成功率分母包含供应商失败和 429，速度仅统计成功且有有效测量的调用。刚完成升级时实时指标从新调用开始积累。

历史接口 `/stats` 与 `/attempts` 只读 SQL，接收 `start_timestamp`、`end_timestamp`（Unix 秒，左闭右开）、`supplier_id`、`pool_id`、`model`、`group_name`。明细传 `p`、`page_size`（1–100）返回 `{items,total,page,page_size}`；未传 `p` 保留原数组响应。历史按请求发起时间检索，与实时完成时间口径不同。原始调用继续存入 `supplier_attempts`，无需新增表；保留期沿用现有数据管理策略。

历史概览和成本与明细使用同一筛选范围，首发与重试按请求去重，排除探测/建议。首次份额是选定范围内的实际观测值，不能累加同一供应商的重复明细行。单位成功请求成本为同币种总采购支出 / 范围内成功请求数，包含失败与重试；存在待核对费用时仅为暂估。这里不将预估节省额当作实际毛利。

## 启用与回退

1. 所有访问同一资源池的网关先升级，并共享 Redis 单主库。保留原分支，不合并 `mozia`。
2. 配置渠道、供应商、已验收模型及采购价。验收记录可使用人工验证结论，容量报告不是必填项。
3. 新建 `adaptive` 规则。已有 `capacity/share/failover` 规则保留原意，不自动切换；旧容量均衡要求完整声明容量，避免把未知容量误算为空闲。
4. 开启动态调度，先“仅观察调度建议”。建议不调用未选中的上游、不预占容量，也不能据此证明成本或体验改善。
5. 关闭观察，按客户 ID 稳定分桶提高灰度比例；0% 观察、100% 对全部匹配请求生效。
6. 回退优先关闭动态调度或恢复规则版本。已绑定资源仍执行声明的容量保护，不重放已经输出内容的流式请求。

Redis 丢失、不可达或发布不确定时保守拒绝。确认旧执行结束并核对 `pending/unknown`、至少 61 秒无供应商调用后才能重建账本；不能删键解除限流。Redis 需持久化、避免淘汰键；当前不支持 Cluster 跨槽执行。保存了新模式或未声明容量后，旧二进制不能直接接管，应先恢复兼容配置并处理在途调用。
